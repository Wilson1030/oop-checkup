        关联标准：Data Clump / Long Parameter List
        出处：Fowler《重构》坏味道 #3 #4
────────────────────────────────────────────────────────────

  (String ip, String port)  跨 3 个类、7 个方法，共出现 7 次

      Init.java:109   update_db_settings(String ip, String port, String db, String user, String psw, String cfg)
      Link.java:33   create_database(String ip, String port, String db, String name, String psw)
      Link.java:41   connect(String ip, String port, String db, String name, String psw, String cfg)
      SqlIO.java:4   get_export_head(String ip, String port, String name, String psw)
      SqlIO.java:8   exportAll(String ip, String port, String db, String name, String psw, String path)
      SqlIO.java:17   export(String ip, String port, String db, String name, String psw, String path, String[] dt)
      SqlIO.java:30   importAll(String ip, String port, String db, String name, String psw, String path)

    ▸ 发生了什么
      (String ip, String port) 这 2 个参数，在 Init、Link、
      SqlIO 共 3 个类的 7 个方法里重复出现。

    ▸ 你在 C 里会怎么写
      你在 C 里遇到这种情况会怎么写？
      如果这几个东西是一个整体，你多半会定义一个 struct，然后
      传指针 ——
      因为拆开传又累，参数顺序还容易写反。

      那你为什么在 Java 里没这么做？
      多半是因为「定义一个类」看起来比「定义一个 struct」重得
      多，
      而你被教成「类是很严肃的东西，不能随便建」。这个观念是错
      的。

    ▸ 为什么是问题
      如果它们确实是一个整体：参数顺序写反时编译器往往不报错（
      类型相同），
      要到运行时才炸；以后加一个字段，你得同时改 7 处方法签
      名。

    ▸ 怎么判断
      这一条需要你自己判断 —— 请回答一个问题：

          你能给 ip、port 起一个名字吗？

          起得出来  →  它们就该是一个类：

              class /* 你起的那个名字 */ {
                  String ip;
                  String port;
              }

          起不出来  →  忽略本条，它们只是碰巧同名。

      如果起出来了，再往前一步 —— 这才是「面向对象」的部分：
      既然这个新类掌握了全部信息，那么操作这些数据的方法
      本来就该长在它身上，而不是留在那 7 个地方。
      C 的 struct 和 Java 的对象，唯一的区别就是：对象能带上操
      作自己的函数。

    ▸ 但要注意
      本条为「待确认」而非「违反」，因为「这几个参数是不是同一
      个概念」
      无法由代码结构判断，只能由写代码的人判断。
      而做这个判断的过程，恰恰就是面向对象设计本身。

    ▸ 你在 C 里会怎么写
      这就是 C 的全局变量。
      你在 C 里写  int g_count;
      在 Java 里写  static int count;
      语义上是同一个东西 —— 一块所有代码都能读写的内存。

    ▸ 为什么是问题
      任何一处代码都能改它，出问题时你无法知道是谁在什么时候改

      如果程序有多线程，它还会直接导致数据竞争。

    ▸ 试试
      问自己一个问题：这个状态属于谁？

          属于某个具体的东西  →  变成那个对象的实例字段
          属于整个程序        →  也应该有一个对象来持有它，
                                  并且只通过方法访问

      把 DbCtrl 的这些字段改成实例字段，然后把 DbCtrl 变成一个
      正常的对象。

    ▸ 但要注意
      常量（static final）不在此列，那是正常且推荐的。
      真正需要全局唯一的资源（连接池、配置），可以用单例，
      但要把访问收敛到方法里，而不是直接暴露字段。

  [中等] 检查项 5 · 封装是否完整
        违反标准：public 可变字段暴露内部表示
        出处：Fowler《重构》坏味道 #5 关联
────────────────────────────────────────────────────────────

  Login  —  1 个 public 可变字段

      Login.java:9   class Login
          public boolean suc

    ▸ 发生了什么
      Login 有 1 个 public 且可变的字段：
          public boolean suc

    ▸ 你在 C 里会怎么写
      C 的 struct 成员本来就是全公开的，你直接写 s.field = x 
      就行，
      语言也没提供别的选择。
      你把这个习惯原样带到了 Java —— 只是把 struct 换成了 
      class。

    ▸ 为什么是问题
      任何代码都能绕过 Login 的逻辑直接改它的字段。
      这意味着：你想加一条规则（比如「数量不能是负数」）时，没
      有地方可以加 ——
      因为根本没有一个必经的入口。

    ▸ 试试
      先把这些字段改成 private，然后编译。
      编译器报错的每一处，都是外部在直接操作 Login 的内部状
      态。

      对每一处报错问一句：
          「这个操作，是不是本来就该由 Login 自己提供一个方法
          来完成？」

      多数情况下答案是「是」。这个过程会自动把行为拉回到数据所
      在的地方 ——
      顺便也就解决了检查项 1。

    ▸ 但要注意
      public final 字段是安全的，不在此列。
      纯数据传输对象（DTO/VO）可以不封装，本工具已按命名惯例排
      除。
      另外，无脑给每个字段配一对 getter/setter 并不等于封装 —
      —
      那只是把 public 换了种写法。

      有地方可以加 ——
      因为根本没有一个必经的入口。

    ▸ 试试
      先把这些字段改成 private，然后编译。
      编译器报错的每一处，都是外部在直接操作 TbStu 的内部状
      态。

      对每一处报错问一句：
          「这个操作，是不是本来就该由 TbStu 自己提供一个方法
          来完成？」

      多数情况下答案是「是」。这个过程会自动把行为拉回到数据所
      在的地方 ——
      顺便也就解决了检查项 1。

    ▸ 但要注意
      public final 字段是安全的，不在此列。
      纯数据传输对象（DTO/VO）可以不封装，本工具已按命名惯例排
      除。
      另外，无脑给每个字段配一对 getter/setter 并不等于封装 —
      —
      那只是把 public 换了种写法。
