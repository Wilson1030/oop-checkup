  [中等] 检查项 1 · 数据与行为是否结合
        违反标准：Anemic Domain Model
        出处：Martin Fowler, AnemicDomainModel, 2003
────────────────────────────────────────────────────────────

  User  —  3 个字段，6 个 getter/setter，0 个业务方法

      User.java:6   class User
          BorrowRecordPage  访问它 6 次
          BookQuery  访问它 3 次
          Book  访问它 2 次
          BorrowRecordQuery  访问它 2 次
          BorrowRecord  访问它 1 次

    ▸ 发生了什么
      User 有 3 个字段、6 个 getter/setter，但没有任何业务方法
      —— 它只是一个数据容器。
      项目里有 6 个其他类、共 15 处在读写它的数据：Book、
      BorrowRecord、BorrowRecordPage、UserPage 等 6 项

    ▸ 你在 C 里会怎么写
      这正是 C 的写法：一个 struct 存数据，一组函数在外面操作
      它。
      你把 struct 改名叫 class，把那些函数搬进了另一个类，
      但结构一点没变 —— 数据在一边，操作数据的代码在另一边。

      在 C 里你别无选择，语言就只给了 struct。
      在 Java 里你有选择，只是没用上。

    ▸ 为什么是问题
      User 的字段含义，只有外面那些类知道。
      哪天你改了某个字段的含义，编译器不会告诉你外部那 15 处逻
      辑已经失效 ——
      你只能靠自己记得。这正是 C 项目越写越难改的原因。

    ▸ 试试
      找一个只用到 User 自己字段的方法，把它搬进 User。
      搬完你会发现：它不再需要参数了 —— 因为数据就在手边。

      这就是「对象」这个词的全部含义：数据，加上操作这些数据的
      函数，
      被放在同一个地方。不是继承，不是多态，就是这个。

    ▸ 但要注意
      不是所有逻辑都该搬进来。涉及多个对象协作、或依赖外部资源
      （数据库、网络、界面）的逻辑，留在 Service 里是对的。
      另外，如果 User 本来就是纯粹的数据传输对象，那贫血是合理
      设计。

  [待确认] 检查项 2 · 是否避免散装参数传递
        关联标准：Data Clump / Long Parameter List
        出处：Fowler《重构》坏味道 #3 #4
────────────────────────────────────────────────────────────

  (String username, String password)  跨 2 个类、3 个方法，共
  出现 3 次

      User.java:13   User(long id, String username, String password)
      UserQuery.java:36   queryUser(String username, String password)
      UserQuery.java:66   registerUser(String username, String password)

    ▸ 发生了什么
      (String username, String password) 这 2 个参数，在 
      User、UserQuery 共 2 个类的 3 个方法里重复出现。

    ▸ 你在 C 里会怎么写
      你在 C 里遇到这种情况会怎么写？
      如果这几个东西是一个整体，你多半会定义一个 struct，然后
      传指针 ——
      因为拆开传又累，参数顺序还容易写反。

      那你为什么在 Java 里没这么做？
      多半是因为「定义一个类」看起来比「定义一个 struct」重得
      多，
      而你被教成「类是很严肃的东西，不能随便建」。这个观念是错
      的。

    ▸ 为什么是问题
      如果它们确实是一个整体：参数顺序写反时编译器往往不报错（
      类型相同），
      要到运行时才炸；以后加一个字段，你得同时改 3 处方法签
      名。

    ▸ 怎么判断
      这一条需要你自己判断 —— 请回答一个问题：

          你能给 username、password 起一个名字吗？

          起得出来  →  它们就该是一个类：

              class /* 你起的那个名字 */ {
                  String username;
                  String password;
              }

          起不出来  →  忽略本条，它们只是碰巧同名。

      如果起出来了，再往前一步 —— 这才是「面向对象」的部分：
      既然这个新类掌握了全部信息，那么操作这些数据的方法
      本来就该长在它身上，而不是留在那 3 个地方。
      C 的 struct 和 Java 的对象，唯一的区别就是：对象能带上操
      作自己的函数。

    ▸ 但要注意
      本条为「待确认」而非「违反」，因为「这几个参数是不是同一
      个概念」
      无法由代码结构判断，只能由写代码的人判断。
      而做这个判断的过程，恰恰就是面向对象设计本身。

  [严重] 检查项 3 · 是否用多态替代类型判断
        违反标准：Switch Statements
        出处：Fowler《重构》坏味道 #11
────────────────────────────────────────────────────────────

  switch 分派 ["1", "2"]  在 3 处重复出现

      BorrowRecordPage.java:34   BorrowRecordPage.borrowBookDetail()
      BorrowRecordPage.java:58   BorrowRecordPage.borrowBook()
      UserPage.java:32   UserPage.loginConsole()

    ▸ 发生了什么
      对 ["1"、"2"] 的类型分派，在 3 处重复出现。

    ▸ 你在 C 里会怎么写
      在 C 里你只能这么做：struct 里放一个 int type 字段，
      然后 switch(type) 分派到不同的处理函数。
      这是 C 唯一能做「同一操作、不同实现」的手段。

      Java 给了你另一个手段，但你还在用 C 的那个。

    ▸ 为什么是问题
      每新增一种类型，你要同时修改这 3 处。
      漏改一处，编译器不会报错 —— 要到运行时走到那个分支才
      炸。
      这就是 Fowler 把它列为坏味道的原因：改动是分散的。

    ▸ 试试
      让每个类型自己实现同一个方法：

          interface Shape { double area(); }
          class Circle implements Shape { public double area()
          { … } }
          class Rect   implements Shape { public double area()
          { … } }

      然后直接调用 shape.area()，由 Java 在运行时选择正确的实
      现。
      新增一种类型时，你只加一个类，一处都不用改。

      这就是多态存在的全部理由 —— 它是 C 那个 switch 分派的
      替代品，
      不是什么高深概念。

    ▸ 但要注意
      如果分支逻辑很简单、而且类型确定不会再增加，保留 switch 
      是可以的。
      多态的代价是逻辑分散到多个文件，看全貌变难了。
      判断标准：这组类型未来还会不会增加？

  [中等] 检查项 4 · static 是否被滥用
        违反标准：全局状态破坏封装
        出处：Java 教科书通识
────────────────────────────────────────────────────────────

  BorrowRecordQuery  —  1 个实例字段，但 8 个方法中 8 个是 
  static（100%）

      BorrowRecordQuery.java:19   class BorrowRecordQuery

    ▸ 发生了什么
      BorrowRecordQuery 的 8 个方法里有 8 个是 static（
      100%）。

    ▸ 你在 C 里会怎么写
      你在写一组 C 函数，只是外面套了一个 class 的壳。
      这里的 class 只起了「命名空间」的作用，和 C 的头文件一样
      ——
      它没有状态，不能被实例化出多个，也谈不上什么对象。

    ▸ 为什么是问题
      static 方法之间只能靠参数传递数据。
      所以你会看到长长的参数列表在这些方法之间来回传 ——
      检查项 2 报出来的那些散装参数，根源往往就在这里。

    ▸ 试试
      观察这些 static 方法反复操作的是哪几个数据。
      把那些数据变成 BorrowRecordQuery 的字段，把方法去掉 
      static 变成实例方法。

      做完你会发现参数列表大幅缩短 —— 因为数据已经在对象里
      了。

    ▸ 但要注意
      纯工具类（数学计算、字符串处理这类无状态的）全 static 是
      正常的，
      本工具已按命名惯例自动排除。
      如果这个类确实是工具类，把它改名为 XxxUtils 即可。

  [中等] 检查项 4 · static 是否被滥用
        违反标准：全局状态破坏封装
        出处：Java 教科书通识
────────────────────────────────────────────────────────────

  DBConnect  —  4 个 static 非 final 字段（全局变量）

      DBConnect.java:10   class DBConnect
          static String DB
          static String username
          static String password
          static Connection connection

    ▸ 发生了什么
      DBConnect 里有 4 个 static 且非 final 的字段：
          static String DB
          static String username
          static String password
          static Connection connection

    ▸ 你在 C 里会怎么写
      这就是 C 的全局变量。
      你在 C 里写  int g_count;
      在 Java 里写  static int count;
      语义上是同一个东西 —— 一块所有代码都能读写的内存。

    ▸ 为什么是问题
      任何一处代码都能改它，出问题时你无法知道是谁在什么时候改
      的。
      调试这类 bug 只能靠通读全部代码。
      如果程序有多线程，它还会直接导致数据竞争。

    ▸ 试试
      问自己一个问题：这个状态属于谁？

          属于某个具体的东西  →  变成那个对象的实例字段
          属于整个程序        →  也应该有一个对象来持有它，
                                  并且只通过方法访问

      把 DBConnect 的这些字段改成实例字段，然后把 DBConnect 变
      成一个正常的对象。

    ▸ 但要注意
      常量（static final）不在此列，那是正常且推荐的。
      真正需要全局唯一的资源（连接池、配置），可以用单例，
      但要把访问收敛到方法里，而不是直接暴露字段。
