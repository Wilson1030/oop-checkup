  ✗ 检查项 1 · 数据与行为是否结合          [中等]
    违反标准：Anemic Domain Model
    出处：Martin Fowler, AnemicDomainModel, 2003
────────────────────────────────────────────────────────────

  Board  —  20 个字段，2 个 getter/setter，0 个业务方法

      Board.java:25   class Board
          Main  访问它 2 次

    ▸ 发生了什么
      Board 有 20 个字段、2 个 getter/setter，但没有任何业务方法
       —— 它只是一个数据容器。
      项目里有 1 个其他类、共 2 处在读写它的数据：Main

    ▸ 你在 C 里会怎么写
      这正是 C 的写法：一个 struct 存数据，一组函数在外面操作它
      。
      你把 struct 改名叫 class，把那些函数搬进了另一个类，
      但结构一点没变 —— 数据在一边，操作数据的代码在另一边。

      在 C 里你别无选择，语言就只给了 struct。
      在 Java 里你有选择，只是没用上。

    ▸ 为什么是问题
      Board 的字段含义，只有外面那些类知道。
      哪天你改了某个字段的含义，编译器不会告诉你外部那 2 处逻辑
      已经失效 ——
      你只能靠自己记得。这正是 C 项目越写越难改的原因。

    ▸ 试试
      找一个只用到 Board 自己字段的方法，把它搬进 Board。
      搬完你会发现：它不再需要参数了 —— 因为数据就在手边。

      这就是「对象」这个词的全部含义：数据，加上操作这些数据的函
      数，
      被放在同一个地方。不是「继承」，不是「多态」，就是这个。

    ▸ 但要注意
      不是所有逻辑都该搬进来。涉及多个对象协作、或依赖外部资源
      （数据库、网络、界面）的逻辑，留在 Service 里是对的。
      另外，如果 Board 本来就是纯粹的数据传输对象，那贫血是合理
      设计。

  ✗ 检查项 2 · 是否避免散装参数传递          [中等]
    违反标准：Data Clump / Long Parameter List
    出处：Fowler《重构》坏味道 #3 #4
────────────────────────────────────────────────────────────

  (int row, int column, int fig_num)  跨 2 个类、2 个方法，共出现 2 次

      Board.java:51   Board(int row, int column, int fig_num)
      Board_Remember.java:51   Board_Remember(int row, int column, int fig_num)

    ▸ 发生了什么
      (int row, int column, int fig_num) 这 3 个参数，在 Board、
      Board_Remember 共 2 个类的 2 个方法里重复出现。

    ▸ 你在 C 里会怎么写
      你在 C 里遇到这种情况会怎么写？
      你多半会定义一个 struct，把这几个字段装进去，然后传它的指
      针。
      因为你知道它们是一个整体 —— 拆开传又累，参数顺序还容易写
      反。

      那你为什么在 Java 里没这么做？
      多半是因为「定义一个类」看起来比「定义一个 struct」重得多
      ，
      而你被教成「类是很严肃的东西，不能随便建」。这个观念是错的
      。

    ▸ 为什么是问题
      参数顺序写反时编译器往往不报错（类型相同），要到运行时才炸
      。
      以后要给这组数据加一个字段，你得同时改 2 处方法签名，漏一
      处就编译不过。

    ▸ 试试
      把它们收进一个类：

          class /* 你来起个名字 */ {
              int row;
              int column;
              int fig_num;
          }

      这 2 个方法的参数列表会全部缩成 1 个。
      起名这一步很重要 —— 如果起不出名字，说明它们可能确实不是
      一个概念。

      再往前一步，这才是「面向对象」的部分：
      既然这个新类掌握了 row、column、fig_num 的全部信息，那么 B
      oard() 这样的方法
      本来就该长在它身上，而不是留在外面。
      C 的 struct 和 Java 的对象，唯一的区别就是：对象能带上操作
      自己的函数。

    ▸ 但要注意
      如果这几个参数在业务上确实无关、只是碰巧同类型同名，那就不
      必封装。
      判断标准只有一条：它们是不是同一件事的组成部分。
