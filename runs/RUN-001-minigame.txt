  [中等] R1 · 参数团
  (int row, int column, int fig_num)  出现 2 次

      Board.java:51   Board(int row, int column, int fig_num)
      Board_Remember.java:51   Board_Remember(int row, int column, int fig_num)

    ▸ 发生了什么
      这 3 个参数在 2 个方法里永远一起出现。当几个数
      据总是结伴而行，说明它们本来就是一个东西。

    ▸ 为什么是问题
      以后要给这组数据加一个新字段，你得同时改 2 处
      方法签名，漏改一处就编译不过；而参数顺序写错时
      ，编译器往往不会报错。

    ▸ 试试
      把 row、column、fig_num 封装成一个类，这 2 个
      方法的参数列表都会缩成 1 个。

    ▸ 但要注意
      如果这几个参数只是碰巧同名同类型、业务上毫无关
      系，那就不必封装。判断标准是：它们在概念上是不
      是同一件事的组成部分。

  [中等] R2 · 贫血模型
  Board  —  20 个字段，2 个 getter/setter，0 个业务方法

      Board.java:25   class Board
          Main  访问它 2 次

    ▸ 发生了什么
      Board 有 20 个字段，却没有任何业务方法 —— 它
      只是一个数据容器。而项目里有 1 个其他类、共 2 
      处在读写它的数据。

    ▸ 为什么是问题
      数据在一个地方，操作数据的代码在另一个地方。Bo
      ard 的字段含义只有外部那些类知道；哪天你改了字
      段，编译器不会告诉你外部哪些逻辑已经失效了。

    ▸ 试试
      找一个只用到 Board 自己字段的方法，把它搬进 Bo
      ard。搬完你会发现它不再需要参数了 —— 因为数
      据就在手边。这就是「对象」的意思。

    ▸ 但要注意
      不是所有逻辑都该搬进来。涉及多个对象协作、或依
      赖外部资源（数据库、网络、UI）的逻辑，留在 Ser
      vice 里是对的。另外，如果 Board 本来就是纯粹的
      数据传输对象，那贫血是合理的。
