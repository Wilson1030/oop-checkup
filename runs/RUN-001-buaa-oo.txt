  [中等] R1 · 参数团
  (int start, int end)  出现 3 次

      Person.java:11   Person(PersonRequest personRequest, int start, int end)
      Person.java:37   changestrategy(int start, int end)
      RequestQueue.java:124   dfs(ArrayList<ArrayList<Integer>> arrayList, int depth, int start, int end, int[] flag, ArrayList<Integer> elevatornum)

    ▸ 发生了什么
      这 2 个参数在 3 个方法里永远一起出现。当几个数
      据总是结伴而行，说明它们本来就是一个东西。

    ▸ 为什么是问题
      以后要给这组数据加一个新字段，你得同时改 3 处
      方法签名，漏改一处就编译不过；而参数顺序写错时
      ，编译器往往不会报错。

    ▸ 试试
      把 start、end 封装成一个类，这 3 个方法的参数
      列表都会缩成 1 个。

    ▸ 但要注意
      如果这几个参数只是碰巧同名同类型、业务上毫无关
      系，那就不必封装。判断标准是：它们在概念上是不
      是同一件事的组成部分。

  [严重] R2 · 贫血模型
  Global  —  3 个字段，0 个 getter/setter，0 个业务方法

      Global.java:3   class Global
          Expression  访问它 10 次
          Factor  访问它 8 次
          Term  访问它 8 次
          Exponent  访问它 6 次
          ExpFactor  访问它 4 次

    ▸ 发生了什么
      Global 有 3 个字段，却没有任何业务方法 —— 它
      只是一个数据容器。而项目里有 10 个其他类、共 5
      2 处在读写它的数据。

    ▸ 为什么是问题
      数据在一个地方，操作数据的代码在另一个地方。Gl
      obal 的字段含义只有外部那些类知道；哪天你改了
      字段，编译器不会告诉你外部哪些逻辑已经失效了。

    ▸ 试试
      找一个只用到 Global 自己字段的方法，把它搬进 G
      lobal。搬完你会发现它不再需要参数了 —— 因为
      数据就在手边。这就是「对象」的意思。

    ▸ 但要注意
      不是所有逻辑都该搬进来。涉及多个对象协作、或依
      赖外部资源（数据库、网络、UI）的逻辑，留在 Ser
      vice 里是对的。另外，如果 Global 本来就是纯粹
      的数据传输对象，那贫血是合理的。
