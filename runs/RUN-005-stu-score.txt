  [严重] 检查项 3 · 是否用多态替代类型判断
        违反标准：Switch Statements
        出处：Fowler《重构》坏味道 #11
────────────────────────────────────────────────────────────

  switch 分派 ["0", "1", "2"]  在 7 处重复出现

      Course.java:168   Course.editCourse()
      courseManage.java:73   courseManage.courseMenu2()
      scoreManage.java:73   scoreManage.scoreMenu2()
      studentManage.java:73   studentManage.studentMenu()
      studentManage.java:104   studentManage.studentMenu2()
      User.java:296   User.editUser2()
      userManage.java:68   userManage.userMenu2()

    ▸ 发生了什么
      对 ["0"、"1"、"2"] 的类型分派，在 7 处重复出现。

    ▸ 你在 C 里会怎么写
      在 C 里你只能这么做：struct 里放一个 int type 字段，
      然后 switch(type) 分派到不同的处理函数。
      这是 C 唯一能做「同一操作、不同实现」的手段。

      Java 给了你另一个手段，但你还在用 C 的那个。

    ▸ 为什么是问题
      每新增一种类型，你要同时修改这 7 处。
      漏改一处，编译器不会报错 —— 要到运行时走到那个分支才
      炸。
      这就是 Fowler 把它列为坏味道的原因：改动是分散的。

    ▸ 试试
      让每个类型自己实现同一个方法：

          interface Shape { double area(); }
          class Circle implements Shape { public double area()
          { … } }
          class Rect   implements Shape { public double area()
          { … } }

      然后直接调用 shape.area()，由 Java 在运行时选择正确的实
      现。
      新增一种类型时，你只加一个类，一处都不用改。

      这就是多态存在的全部理由 —— 它是 C 那个 switch 分派的
      替代品，
      不是什么高深概念。

    ▸ 但要注意
      如果分支逻辑很简单、而且类型确定不会再增加，保留 switch 
      是可以的。
      多态的代价是逻辑分散到多个文件，看全貌变难了。
      判断标准：这组类型未来还会不会增加？

  [中等] 检查项 4 · static 是否被滥用
        违反标准：全局状态破坏封装
        出处：Java 教科书通识
────────────────────────────────────────────────────────────

  Course  —  1 个 static 非 final 字段（全局变量）

      Course.java:16   class Course
          static String classPath

    ▸ 发生了什么
      Course 里有 1 个 static 且非 final 的字段：
          static String classPath

    ▸ 你在 C 里会怎么写
      这就是 C 的全局变量。
      你在 C 里写  int g_count;
      在 Java 里写  static int count;
      语义上是同一个东西 —— 一块所有代码都能读写的内存。

    ▸ 为什么是问题
      任何一处代码都能改它，出问题时你无法知道是谁在什么时候改
      的。
      调试这类 bug 只能靠通读全部代码。
      如果程序有多线程，它还会直接导致数据竞争。

    ▸ 试试
      问自己一个问题：这个状态属于谁？

          属于某个具体的东西  →  变成那个对象的实例字段
          属于整个程序        →  也应该有一个对象来持有它，
                                  并且只通过方法访问

      把 Course 的这些字段改成实例字段，然后把 Course 变成一个
      正常的对象。

    ▸ 但要注意
      常量（static final）不在此列，那是正常且推荐的。
      真正需要全局唯一的资源（连接池、配置），可以用单例，
      但要把访问收敛到方法里，而不是直接暴露字段。
