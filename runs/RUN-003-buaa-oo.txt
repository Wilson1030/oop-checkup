  [严重] 检查项 1 · 数据与行为是否结合
        违反标准：Anemic Domain Model
        出处：Martin Fowler, AnemicDomainModel, 2003
────────────────────────────────────────────────────────────

  Global  —  3 个字段，0 个 getter/setter，0 个业务方法

      Global.java:3   class Global
          Expression  访问它 10 次
          Factor  访问它 8 次
          Term  访问它 8 次
          Exponent  访问它 6 次
          ExpFactor  访问它 4 次

    ▸ 发生了什么
      Global 有 3 个字段、0 个 getter/setter，但没有任何业务方
      法 —— 它只是一个数据容器。
      项目里有 10 个其他类、共 52 处在读写它的数据：
      ExpFactor、Exponent、Expression、Factor 等 10 项

    ▸ 你在 C 里会怎么写
      这正是 C 的写法：一个 struct 存数据，一组函数在外面操作
      它。
      你把 struct 改名叫 class，把那些函数搬进了另一个类，
      但结构一点没变 —— 数据在一边，操作数据的代码在另一边。

      在 C 里你别无选择，语言就只给了 struct。
      在 Java 里你有选择，只是没用上。

    ▸ 为什么是问题
      Global 的字段含义，只有外面那些类知道。
      哪天你改了某个字段的含义，编译器不会告诉你外部那 52 处逻
      辑已经失效 ——
      你只能靠自己记得。这正是 C 项目越写越难改的原因。

    ▸ 试试
      找一个只用到 Global 自己字段的方法，把它搬进 Global。
      搬完你会发现：它不再需要参数了 —— 因为数据就在手边。

      这就是「对象」这个词的全部含义：数据，加上操作这些数据的
      函数，
      被放在同一个地方。不是继承，不是多态，就是这个。

    ▸ 但要注意
      不是所有逻辑都该搬进来。涉及多个对象协作、或依赖外部资源
      （数据库、网络、界面）的逻辑，留在 Service 里是对的。
      另外，如果 Global 本来就是纯粹的数据传输对象，那贫血是合
      理设计。

  [待确认] 检查项 2 · 是否避免散装参数传递
        关联标准：Data Clump / Long Parameter List
        出处：Fowler《重构》坏味道 #3 #4
────────────────────────────────────────────────────────────

  (int start, int end)  跨 2 个类、3 个方法，共出现 3 次

      Person.java:11   Person(PersonRequest personRequest, int start, int end)
      Person.java:37   changestrategy(int start, int end)
      RequestQueue.java:124   dfs(ArrayList<ArrayList<Integer>> arrayList, int depth, int start, int end, int[] flag, ArrayList<Integer> elevatornum)

    ▸ 发生了什么
      (int start, int end) 这 2 个参数，在 Person、
      RequestQueue 共 2 个类的 3 个方法里重复出现。

    ▸ 你在 C 里会怎么写
      你在 C 里遇到这种情况会怎么写？
      如果这几个东西是一个整体，你多半会定义一个 struct，然后
      传指针 ——
      因为拆开传又累，参数顺序还容易写反。

      那你为什么在 Java 里没这么做？
      多半是因为「定义一个类」看起来比「定义一个 struct」重得
      多，
      而你被教成「类是很严肃的东西，不能随便建」。这个观念是错
      的。

    ▸ 为什么是问题
      如果它们确实是一个整体：参数顺序写反时编译器往往不报错（
      类型相同），
      要到运行时才炸；以后加一个字段，你得同时改 3 处方法签
      名。

    ▸ 怎么判断
      这一条需要你自己判断 —— 请回答一个问题：

          你能给 start、end 起一个名字吗？

          起得出来  →  它们就该是一个类：

              class /* 你起的那个名字 */ {
                  int start;
                  int end;
              }

          起不出来  →  忽略本条，它们只是碰巧同名。

      如果起出来了，再往前一步 —— 这才是「面向对象」的部分：
      既然这个新类掌握了全部信息，那么操作这些数据的方法
      本来就该长在它身上，而不是留在那 3 个地方。
      C 的 struct 和 Java 的对象，唯一的区别就是：对象能带上操
      作自己的函数。

    ▸ 但要注意
      本条为「待确认」而非「违反」，因为「这几个参数是不是同一
      个概念」
      无法由代码结构判断，只能由写代码的人判断。
      而做这个判断的过程，恰恰就是面向对象设计本身。

  [中等] 检查项 3 · 是否用多态替代类型判断
        违反标准：Switch Statements
        出处：Fowler《重构》坏味道 #11
────────────────────────────────────────────────────────────

  instanceof 链 [ElevatorRequest, MaintainRequest, 
  PersonRequest]  3 个类型分支

      RequestQueue.java:37   RequestQueue.addRequest()

    ▸ 发生了什么
      对 [ElevatorRequest、MaintainRequest、PersonRequest] 的
      类型分派，使用了 instanceof 链。

    ▸ 你在 C 里会怎么写
      在 C 里你只能这么做：struct 里放一个 int type 字段，
      然后 switch(type) 分派到不同的处理函数。
      这是 C 唯一能做「同一操作、不同实现」的手段。

      Java 给了你另一个手段，但你还在用 C 的那个。

    ▸ 为什么是问题
      每新增一种类型，这个判断链就要加一个分支。
      链越长，越容易漏掉某种情况，而编译器帮不上忙。

    ▸ 试试
      让每个类型自己实现同一个方法：

          interface Shape { double area(); }
          class Circle implements Shape { public double area()
          { … } }
          class Rect   implements Shape { public double area()
          { … } }

      然后直接调用 shape.area()，由 Java 在运行时选择正确的实
      现。
      新增一种类型时，你只加一个类，一处都不用改。

      这就是多态存在的全部理由 —— 它是 C 那个 switch 分派的
      替代品，
      不是什么高深概念。

    ▸ 但要注意
      如果分支逻辑很简单、而且类型确定不会再增加，保留 if-else
      是可以的。
      多态的代价是逻辑分散到多个文件，看全貌变难了。
      判断标准：这组类型未来还会不会增加？

  [严重] 检查项 5 · 封装是否完整
        违反标准：public 可变字段暴露内部表示
        出处：Fowler《重构》坏味道 #5 关联
────────────────────────────────────────────────────────────

  Global  —  3 个 public 可变字段

      Global.java:3   class Global
          public Random r
          public int now
          public int def

    ▸ 发生了什么
      Global 有 3 个 public 且可变的字段：
          public Random r
          public int now
          public int def

    ▸ 你在 C 里会怎么写
      C 的 struct 成员本来就是全公开的，你直接写 s.field = x 
      就行，
      语言也没提供别的选择。
      你把这个习惯原样带到了 Java —— 只是把 struct 换成了 
      class。

    ▸ 为什么是问题
      任何代码都能绕过 Global 的逻辑直接改它的字段。
      这意味着：你想加一条规则（比如「数量不能是负数」）时，没
      有地方可以加 ——
      因为根本没有一个必经的入口。

    ▸ 试试
      先把这些字段改成 private，然后编译。
      编译器报错的每一处，都是外部在直接操作 Global 的内部状
      态。

      对每一处报错问一句：
          「这个操作，是不是本来就该由 Global 自己提供一个方法
          来完成？」

      多数情况下答案是「是」。这个过程会自动把行为拉回到数据所
      在的地方 ——
      顺便也就解决了检查项 1。

    ▸ 但要注意
      public final 字段是安全的，不在此列。
      纯数据传输对象（DTO/VO）可以不封装，本工具已按命名惯例排
      除。
      另外，无脑给每个字段配一对 getter/setter 并不等于封装 —
      —
      那只是把 public 换了种写法。
